# 实现架构总纲

本文规定工程目录、模块职责、依赖方向、数据流、规则承载层、资源归档、测试边界和禁止越权边界。规则权威见 `游戏规则总纲.md`，当前活跃内容见 `数据与内容总表.md`。

本文档记录当前有效架构，不保留历史修改记录、讨论过程、临时解释和失败原因。

---

## 3. 命名、ID 和职责命名

### 3.1 命名规则

```text
文件名：PascalCase.gd / PascalCase.tscn。
目录名：lower_snake_case。
数据 id：lower_snake_case。
本地化 key：namespace.id.field。
显示名：本地化或显示字段，不作为底层规则 id。
```

### 3.2 稳定 ID

```text
card_id：卡牌规则标识。
job_id：可选职业 / 角色标识。
character_id：单位模板标识。
enemy_deck_id：敌方牌包模板标识。
event_id：事件标识。
status_id：状态标识。
effect_id：效果步骤或特殊效果标识。
audio_event_id：音频事件标识。
visual_profile_id：视觉 profile 标识。
```

规则引用优先使用 id、标签和字段，不使用玩家可见名称。

### 3.3 脚本职责名

```text
Manager：流程调度、上下文切换。
Rules：纯规则判定、计算、合法性。
Resolver：流程编排，调用 Rules 和 Effect。
Service：探索、奖励、商店、事件等非战斗业务入口。
Database：定义、索引、过滤、兼容门面。
View / UI：展示和交互。
Controller：控制器决策，提交请求。
Store：保存、读取和迁移。
Factory：生成运行时对象或 UI 结构。
Router：事件到音频、浮字、动画等反馈映射。
Snapshot / ViewModel：UI 展示数据快照。
```

单文件不同时承担 Manager、Rules、Resolver、Database、UI 职责。

## 4. 总体架构原则

```text
数据描述事实和配置。
规则系统解释数据。
UI 展示状态并提交请求。
AI 读取可见状态并提交合法请求。
测试入口走同一请求和规则流程。
```

```text
玩家和敌方共用战斗底层、卡牌定义、效果解释、区域、单位、状态、装备、事件、响应链和胜负规则。
```

```text
构筑系统只属于玩家。
敌方不构筑，不拥有备牌区、构筑分、获得卡牌和卡组调整流程。
敌方牌库由预设敌方牌包模板生成。
```

```text
卡牌数据库是统一规则对象库，不按敌我归属拆分。
玩家卡、敌方卡、废卡、干扰卡、职业卡均引用同一套卡牌定义。
```

```text
职业是玩家可选身份包装。
职业引用主单位模板、固定初始牌组、职业卡池、局外成长和职业机制。
职业不塞回角色池。
```

```text
角色池是通用单位模板库。
玩家主单位、普通敌人、精英敌人、Boss、召唤单位均来自单位模板。
角色模板不反向绑定敌方牌包。
```

```text
新增规则能力优先落入对应 Rules 模块。
禁止为了单卡、单敌人、单 UI、单事件写长期硬编码分支。
```

## 5. 分层结构和依赖方向

### 5.1 架构分层

```text
运行状态层：探索内状态、局外成长、当前卡组、备牌区、灵石、地图节点、战斗入口参数。
数据装配层：按职业、卡池、敌方牌包模板、难度曲线和遭遇类型组装进入战斗的数据。
战斗实例层：生成单场战斗区域，包括牌库、手牌、墓地、除外区、放置区、装备 / 附着物、单位和临时状态。
请求校验层：统一处理玩家点击、拖拽、AI 出牌和测试调用的卡牌发动请求、目标选择、区域合法性、条件和去向。
事件响应层：承载战斗事件、事件驱动时点、响应窗口、响应链、强制触发、可选触发和后发先至结算。
效果解释层：解释伤害、失去生命、治疗、状态、抽牌、检索、区域移动、装备、破坏、反制、解除、召唤和行动额度变化。
展示交互层：订阅快照和事件，只负责展示、选择、确认、取消和提交请求。
反馈表现层：根据事件播放浮字、音效、动画、震动和提示。
```

### 5.2 依赖方向

```text
数据定义 → 数据装配 → 运行状态 → 战斗实例 → Rules → Resolver → UI / AI 请求入口
```

允许方向：

```text
UI 读取 Snapshot / ViewModel，提交 Request。
AI 读取可见 Snapshot，提交 Request。
Resolver 调用 Rules 和 EffectResolver。
Rules 读取数据定义和运行状态，返回判定结果。
BattleManager 调度流程，不写具体规则细则。
RunState 接收探索结果，不解释卡牌战斗效果。
Database 提供定义，不持有战斗运行状态。
Audio / Visual 只消费反馈事件，不反向决定规则。
```

禁止方向：

```text
UI 直接改战斗状态。
AI 直接改战斗状态。
Database 调用 UI。
卡牌数据调用场景节点。
角色模板反向选择敌方牌包。
RewardService 直接改 UI。
ShopService 直接改 UI。
EventService 直接改 UI。
规则模块硬写音频、美术、节点路径。
```

## 6. 核心数据流

### 6.1 探索启动流

```text
职业选择
→ CharacterPrepScene 展示准备信息
→ MetaProgression 读取职业成长
→ CardPoolDatabase 装配当前可获得卡池
→ RunState 创建本轮探索状态
→ MapGenerator 创建地图
→ MapScene 展示探索地图
```

### 6.2 节点战斗流

```text
节点选择
→ EncounterFactory 根据层级 / 节点 / 世界难度 / 遭遇类型选择敌方牌包模板
→ BattleEncounterRuntime 生成战斗入口数据
→ BattleManager 创建 BattleContext
→ BattleSide / DeckManager 创建双方战斗区域
→ BattleUI 读取 BattleSnapshot
→ 玩家 UI / EnemyAIController 提交 BattleRequest
→ CardActivationRules / CardTargetRules / UnitActionRules 校验
→ ResponseChainRules 处理响应链
→ EffectResolver 解释效果步骤
→ BattleEventRules 生成事件
→ VictoryRules 检查胜负
→ BattleCleanupRules 清理战斗实例
→ RewardService 生成奖励入口
→ RunState 接收生命变化、奖励入口、节点完成结果
```

### 6.3 奖励入卡流

```text
RewardService 生成候选
→ RewardSnapshot 展示候选
→ 玩家选择奖励
→ CardAcquisitionRules 判断进入当前卡组或备牌区
→ DeckBuildRules 校验当前卡组上限和构筑分
→ RunState 写入探索状态
→ MapScene 回到地图
```

### 6.4 坊市流

```text
ShopService 生成商品
→ ShopSnapshot 展示商品、价格、刷新费用、出售列表
→ 玩家提交购买 / 出售 / 刷新请求
→ ShopService 校验灵石、商品、备牌区卡牌
→ CardAcquisitionRules / RunState 写入结果
```

### 6.5 结算流

```text
玩家主单位生命归零 或 第三层 Boss 击败
→ RunSettlement 计算修为点
→ MetaProgression 写入职业成长货币和解锁状态
→ RunState 清空本轮探索状态
→ SaveStore 保存局外数据
```

## 7. Autoload 和全局服务

允许 Autoload：

```text
SceneRouter / SceneManager：场景切换。
SettingsStore：设置保存和读取。
SaveStore：局外存档保存和读取。
LocalizationService：本地化查询。
AudioManager / MusicManager：音频播放入口。
GameSettings：全局设置运行副本。
DataRegistry：启动后稳定数据索引入口。
```

禁止 Autoload：

```text
当前战斗状态。
当前手牌、牌库、墓地。
当前响应链。
当前目标选择。
当前敌方 AI 临时评分。
当前奖励候选。
当前商店临时库存。
```

战斗状态属于 BattleContext。探索状态属于 RunState。局外持久状态属于 SaveStore / MetaProgression。

## 9. 运行状态对象边界

### 9.1 RunState

保存一次探索内状态：

```text
run_id。
当前职业 job_id。
玩家主单位当前生命。
探索层基础攻击 / 防御修正。
当前卡组。
备牌区。
灵石。
当前层。
当前节点位置。
地图节点状态。
本轮随机种子。
已触发并明确跨节点持续的事件结果。
局外成长加成副本。
世界难度。
```

不保存：

```text
当前战斗手牌。
当前战斗墓地。
当前响应链。
当前 UI 选中目标。
AI 临时评分。
战斗内临时状态。
```

### 9.2 BattleContext

保存单场战斗状态：

```text
context_id 与请求序号。
双方 BattleSide。
当前回合阵营。
阶段。
当前战斗事件。
响应链状态。
目标选择状态。
战斗事件日志。
本场随机状态。
战斗胜负状态。
```

不保存局外成长、地图节点、商店库存、事件进度和存档字段。

### 9.3 BattleSide

保存阵营牌手战斗区域：

```text
side_id。
控制器类型。
单位列表。
主单位引用。
DeckManager。
手牌。
墓地。
除外区。
放置区。
装备 / 附着物索引。
抽牌数。
可见性规则标记。
```

### 9.4 SaveData

保存局外长期状态：

```text
save_version。
职业修为点。
职业成长项等级。
职业卡池解锁状态。
通用解锁状态。
设置引用。
统计数据。
```

不保存战斗实例、探索临时状态、UI 临时状态、AI 临时状态和响应链。

### 9.5 UIState

保存展示临时状态：

```text
当前 hover 卡牌。
当前打开 tooltip。
当前滚动位置。
当前弹窗。
当前本地筛选条件。
当前动画播放状态。
```

UIState 不作为规则来源。

### 9.6 核心对象字段边界表

```text
RunState 只保存探索层字段。
BattleContext 只保存单场战斗字段。
BattleSide 只保存阵营牌手战斗区域字段。
SaveData 只保存局外长期字段。
UIState 只保存展示临时字段。
```

## 10. Snapshot / ViewModel 结构

UI 读取 Snapshot / ViewModel，不直接绑定核心运行对象。

```text
BattleSnapshot：战斗场面、双方公开信息、手牌展示、单位展示、放置区展示、可用操作摘要。
ResponseWindowSnapshot：当前响应事件、可响应卡牌、可选目标、跳过状态。
MapSnapshot：地图节点、当前位置、可达节点、节点奖励摘要。
DeckBuildSnapshot：当前卡组、备牌区、构筑分、合法性错误。
RewardSnapshot：奖励候选、选择状态、去向提示。
ShopSnapshot：商品、价格、刷新费用、可出售备牌卡。
CharacterPrepSnapshot：职业信息、成长状态、卡池解锁、世界难度。
```

Snapshot 不持有规则对象写权限。UI 通过 request 提交操作。

当前 `BattleSnapshot` / `BattleViewModel`、`RunSnapshot` / `RunViewModel` 和 `CharacterPrepViewModel` 已落地。BattleUI、MapScene 和 CharacterPrepScene 读取深副本视图；命令由 ViewModel 转交唯一运行容器。EnemyAIController 读取 BattleSnapshot，不持有 BattleContext 可变容器。

## 11. 战斗核心模块

### 11.1 BattleManager.gd

职责：

```text
创建和持有 BattleContext。
调度阶段。
接收玩家 / AI 请求。
转发请求给 Resolver 和 Rules。
推进事件和响应链。
接收胜负结果。
输出 BattleResult。
```

当前正式入口以 `BattleRequest` 规范请求身份、阵营、来源、引用、payload 和 context identity，由 `BattleManager.submit_request` / `handle_battle_request` 返回 `BattleResult`。出牌、攻击、防御、目标选择/确认、结束回合、发动/跳过响应和装备替换均使用同一 Request/Result 契约；内部 bool 只用于单次 handler 判定。玩家 UI 通过 `BattleViewModel` 消费明确结果；EnemyAIController 只读取 AI Snapshot，敌方请求由 BattleManager 提交。

禁止：

```text
不硬写卡牌效果。
不直接计算状态规则。
不直接排序响应链细则。
不直接处理 UI 节点。
不直接写 RunState。
不直接播放音频和动画。
```

### 11.2 BattleContext.gd

职责：单场战斗唯一状态容器。BattleManager 的同名访问属性直接转发到该 Context，不复制或镜像状态。CardResolver、EffectResolver 和 EnemyAIController 是 BattleManager 持有的无状态/逻辑依赖，不存入 BattleContext。

禁止：保存探索长期状态、局外成长、UI 临时状态。

### 11.3 BattleSide.gd

职责：阵营牌手包装，持有阵营区域和单位引用。

```text
玩家侧：由 UI 控制。
敌方侧：由 EnemyAIController 控制。
```

### 11.4 DeckManager.gd

职责：管理本场牌库、手牌、墓地、除外区、洗牌、抽牌、检索基础操作。

禁止：修改探索层当前卡组和备牌区。

### 11.5 BattleUnit.gd / UnitRuntime.gd

职责：单场战斗单位运行体。

```text
生命。
攻击。
防御。
状态实例。
装备 / 附着物。
行动额度。
防御姿态。
存活状态。
来源模板。
```

单位不持有卡组，不自行决策行动。

当前单位状态以 `BattleUnit.status_instances` 作为唯一运行状态容器。每个状态实例记录 `instance_id`、`status_id`、`source`、`value`、`counter`、`tags`、`cleanup_scope` 和 `created_order`；`BattleUnit` 提供 `add_status`、`get_status`、`status_value`、`has_status`、`remove_status`、`clear_status`、`clear_statuses`、`status_snapshot` 和 `status_records_snapshot` 等 helper，统一当前状态读写和测试快照口径。`status_records_snapshot()` 返回按创建顺序排列的实例数组；`status_snapshot()` 以 `instance_id` 为 key，不以 `status_id` 覆盖同名实例。

当前装备仍以 `BattleUnit.equipment` 作为唯一运行装备列表源，并以 `equipment_attack_bonus` / `equipment_defense_bonus` 作为当前攻防加成运行源；`BattleUnit` 提供装备查找、挂载、移除、effect kind、bonus 汇总和 `equipment_snapshot` / `equipment_records_snapshot` helper，统一当前装备字段和测试快照口径。完整 `EquipmentRules`、装备响应来源、附着物实例化和永续实例化仍未落地。

战斗规则模块位于 `res://scripts/battle/rules/`。

### 12.1 规则模块清单

```text

BattleCleanupRules.gd：战斗结束清理，战斗实例与探索层回写边界。
CardActivationRules.gd：卡牌发动区域、时点、类型、条件、全局限制。
CardTargetRules.gd：目标模式、目标范围、合法目标、隐藏区目标。
CardMovementRules.gd：卡牌区域移动、原拥有者区域、使用后去向。
UnitActionRules.gd：单位攻击、防御、行动额度、防御姿态。
VictoryRules.gd：死亡、失败、胜利、玩家主单位优先失败。
StatusRules.gd：状态实例、标签、计数器、触发、衰减、驱散。
ContinuousEffectRules.gd：永续、装备、附着物、持续修正来源。
EquipmentRules.gd：装备 / 附着物挂载、离场、破坏、转移。
StatModifierRules.gd：生命、攻击、防御、抽牌数、行动额度等修正计算。
RandomRules.gd：随机源、种子、随机目标、固定种子测试。
```

### 12.2 规则模块边界

```text
Rules 返回判定、候选、数值、错误码。
Rules 不直接改 UI。
Rules 不直接播放音频。
Rules 不直接加载场景。
Rules 不直接保存存档。
Rules 不直接创建奖励 UI。
```

### 12.3 战斗请求处理顺序

```text
请求进入
→ 引用解析
→ 可见性检查
→ 区域检查
→ 发动 / 行动合法性检查
→ 目标检查
→ 响应链处理
→ 效果解释
→ 区域移动
→ 事件生成
→ 胜负检查
→ 结果返回
```

禁止绕过前置检查直接进入效果解释。

### 12.4 Rules 依赖边界

```text
CardActivationRules 可读取 BattleZoneRules、BattleVisibilityRules、CardTargetRules 的判定结果。

StatModifierRules 统一汇总基础值、成长、难度、装备、状态、永续、临时修正。
VictoryRules 读取单位存活状态，不处理奖励和结算数值。
BattleCleanupRules 只清理战斗实例和输出回写结果，不生成奖励候选。
```

## 13. Resolver 和效果解释

### 13.1 CardResolver.gd

职责：卡牌发动流程编排。

输入：

```text
CardPlayRequest。
当前 BattleContext。
当前可见 Snapshot。
```

输出：

```text
CardPlayResult。
事件列表。
错误码。
目标需求。
响应需求。
```

禁止：

```text
不直接解释具体效果。
不直接计算数值修正。
不直接排序响应链。
不直接操作 UI 节点。
不直接改探索卡组。
```

当前 active 卡牌正式路径中，`CardResolver.gd` 只负责发动编排、目标/条件校验、来源卡去向、请求衔接和响应时点；`effect_steps` 的具体解释交给 `EffectResolver.gd`。非 active / legacy 卡牌仍保留旧 `effect.kind` 隔离路径，不作为 active 正式 schema。

### 13.2 EffectResolver.gd

职责：解释通用效果步骤。

通用效果类型：

```text
造成伤害。
失去生命。
治疗。
添加状态。
移除状态。
抽牌。
检索。
向指定区域加入指定卡牌。
区域移动。
装备。
附着。
破坏。
反制 / 无效。
解除 / 驱散。
召唤单位。
改变行动额度。
改变攻击 / 防御。
添加下一次攻击效果。
添加命中后状态效果。
移动来源卡。
无效果。
触发事件。
```

当前 active 卡牌使用 `effect_steps[].effect_type`，由 `EffectResolver.gd` 统一解释 `add_next_attack_modifier`、`add_status_on_hit`、`heal`、`set_unit_action_lock`、`remove_status_by_tag`、`add_status`、`draw_cards`、`create_card_to_zone`、`move_source_card` 和 `no_effect`。

禁止：

```text
不读取玩家可见文本作为规则。
不写单卡专属长期分支。
不直接弹 UI。
不直接保存运行状态到存档。
不绕过 CardMovementRules 移动卡牌。
```

### 13.3 效果步骤字段

```text
effect_type：效果类型。
source_ref：效果来源。
target_mode：目标模式。
target_ref：目标引用。
value：数值。
zone_from：来源区域。
zone_to：目标区域。
filters：筛选条件。
duration：持续时间。
timing：触发时点 / 响应事件。
flags：额外规则标签。
```

未使用字段留空或省略。未声明字段走默认规则。


### 13.4 效果步骤 DSL 约束

效果步骤是数据字段，不是脚本片段。

```text
effect_type 必须来自通用效果类型枚举。
source_ref 必须指向卡牌、状态、装备、单位、事件或系统来源。
target_mode 和 target_scope 必须与卡牌目标规则一致。
zone_from / zone_to 只描述区域，不直接执行移动。
filters 只描述筛选条件，不写脚本表达式。
flags 只使用预定义标签，不写自由规则句。
```

禁止：

```text
在效果步骤中填写函数路径。
在效果步骤中填写 Godot 节点路径。
在效果步骤中填写 UI 文案作为规则。
在效果步骤中用描述文本代替字段。
为单张卡创建专属 resolver 分支。
```

新增 effect_type 必须同步：

```text
游戏规则总纲：若产生新规则能力。
实现架构总纲：若新增承载模块或依赖。
数据与内容总表：若进入活跃内容。
EffectResolver：新增通用解释分支。
DataValidator：新增字段校验。
Rules 测试：新增最小规则样例。
```

### 13.5 效果步骤结果

每个效果步骤返回统一结果：

```text
success。
error_code。
state_changes。
generated_events。
created_refs。
consumed_refs。
followup_requests。
```

效果步骤失败不由 UI 私自处理。失败结果交给 Resolver 决定是否继续后续步骤、终止当前链节或返回错误。

## 14. 事件、响应链和日志

### 14.1 战斗事件

战斗事件由规则层产生。事件用于：

```text
响应候选检查。
战斗记录。
浮字。
音效。
动画。
测试断言。
调试日志。
```

事件不是 UI 文案。UI 文案由事件 id、对象 id 和本地化生成。

### 14.2 响应链

响应链由 ResponseChainRules 维护。

```text
战斗事件进入待结算状态。
系统检查合法响应来源。
无合法响应：事件直接结算。
有合法响应：打开响应窗口。
每次发动响应生成链节。
双方均停止追加响应后，响应链关闭。
响应链关闭后锁定结算。
链节按后发先至顺序一次性结算。
链结算期间不插入新的普通响应窗口。
链中产生的新事件，在当前链结算完成后按新事件处理。
```

### 14.3 响应来源

```text
已盖伏且可触发的防御牌。
明确允许响应的手牌。
明确允许响应的墓地 / 除外区效果。
永续卡。
装备。
附着物。
状态。
单位能力。
其他明确声明可响应的来源。
```

### 14.4 战斗记录

战斗记录由事件生成，不由 UI 手写。战斗记录长度有上限或分页策略。


### 14.5 战斗事件对象字段

BattleEvent 为规则事件对象，不是 UI 文案对象。

当前代码中的最小事件窗口仍使用 `Dictionary`，由 `BattleManager.create_event` 统一补齐基础字段：`event_type`、`source`、`source_key`、`target`、`target_key`、`value`、`cancelled`、`modifiers`、`protected_targets`。`normal_attack`、`attack_source_key`、`attack_source_unit`、`post_steps`、`post_source_unit`、`enemy_side_card` 作为现有兼容扩展字段保留。`open_timing_window`、`resolve_chain`、`resolve_original_event` 和 `CardResolver` 响应入口通过事件字段 helper 读取这些字段；当前仍未对象化为完整 `BattleEvent` / `ResponseChain` / `ChainLink`。

当前 `chain_stack` 仍由 `BattleManager` 维护为 `Dictionary` 数组，链节字段统一为 `card`、`card_uid`、`card_id`、`source_zone`、`controller_side`、`event_type`、`chain_index`、`locked`、`resolved`。最小 `ResponseWindowRules.gd` 已作为无状态 helper 外壳承载 player-only 响应窗口字段、`pass_state` 和 `chain_stack` 链节创建、读取、锁定、已结算标记；`add_card_to_chain`、`skip_response`、`resolve_chain` 的正式流程仍由 `BattleManager` 调度。结算顺序仍为后发先至，实际响应效果仍交给既有 `CardResolver.resolve_chain_card`。

当前响应窗口归属仍为 player-only。`BattleManager` 使用 `response_window_owner_side`、`active_response_side` 和 `response_pass_state` 记录当前玩家响应窗口的拥有方、当前响应方和玩家跳过状态；`skip_response` 只表示玩家跳过当前窗口。敌方响应来源、双方优先权、双方 pass 轮转、事件队列和完整 `ResponseChainRules` 仍未落地。

```text
event_ref：事件实例引用。
event_type：事件类型。
event_state：created / pending_response / locked / resolving / resolved / cancelled。
source_ref：事件来源，允许为空。
controller_side：事件控制方，允许为空。
actor_ref：执行事件的单位、卡牌、状态或效果，允许为空。
target_refs：事件目标引用列表。
zone_from / zone_to：涉及区域移动时使用。
value_payload：伤害、治疗、抽牌数、层数等数值载荷。
rule_payload：事件专用规则载荷。
visibility_scope：public / owner_only / hidden。
response_policy：none / optional / forced / data_driven。
created_by：生成事件的规则模块或链节引用。
sequence_index：本场战斗内事件顺序号。
```

字段规则：

```text
event_type 使用枚举，不用自由文本。
event_state 只由战斗事件层和响应链层推进。
visibility_scope 决定 UI 可见范围，不由 UI 自行判断。
response_policy 决定是否进入响应候选检查。
rule_payload 只能保存规则数据，不保存 UI 节点、动画节点、音频路径或本地化文本。
```

### 14.6 战斗事件生命周期

```text
创建：规则模块产生 BattleEvent。
候选检查：ResponseChainRules 按 response_policy 检查合法响应来源。
锁定：无响应或响应链关闭后，事件进入不可再追加响应状态。
结算：对应规则模块处理事件效果。
完成：事件写入事件日志，生成 Snapshot / ViewModel 可消费事件。
取消：事件被反制、规则阻断或来源失效时进入 cancelled。
```

响应链结算中产生的新事件不插入当前链。当前链结算完成后，新事件按 sequence_index 顺序进入事件处理流程。

### 14.7 响应链对象字段

ResponseChain 为单个待结算事件的响应链对象。

```text
chain_ref：响应链引用。
root_event_ref：触发该链的原始事件。
chain_state：open / locked / resolving / resolved / cancelled。
active_side：当前可响应阵营。
links：链节列表。
pass_state：双方跳过状态。
created_sequence：创建顺序号。
resolved_sequence：结算顺序号，允许为空。
```

链状态规则：

```text
open：允许追加响应。
locked：双方停止追加响应，链节顺序锁定。
resolving：按后发先至结算链节。
resolved：全部链节结算完成。
cancelled：根事件失效或规则终止链。
```

### 14.8 链节对象字段

ChainLink 为响应链中的单次卡牌 / 效果发动。

```text
link_ref：链节引用。
chain_ref：所属响应链。
source_ref：卡牌、状态、装备、永续、单位能力或其他来源。
controller_side：链节控制方。
activation_request：产生该链节的请求引用。
respond_to_event_ref：响应的事件引用。
respond_to_link_ref：响应的上一链节引用，允许为空。
target_refs：链节目标。
effect_steps：本次链节待结算的效果步骤列表。
link_state：declared / negated / resolving / resolved / fizzled / cancelled。
order_index：加入链的顺序。
resolve_index：结算顺序。
result_events：链节结算产生的事件引用列表。
```

链节规则：

```text
链节 declared 后才可被反制。
反制只改变未结算链节的 link_state，不直接回滚已结算结果。
link_state=negated 的链节不结算 effect_steps。
link_state=fizzled 表示目标或条件在结算时失效。
链节不持有 UI 节点、场景节点、按钮引用或动画引用。
```

## 21. 请求、结果、引用和错误码

### 21.1 请求对象

```text

request_type：play_card / unit_attack / unit_defend / spell_attack / select_target / confirm_target / end_turn / play_response / skip_response / choose_equipment_replacement / cancel_equipment_replacement。

payload：请求专用输入字段。
context_id：所属 BattleContext id。
```

玩家、AI、测试入口提交同类请求。

### 21.2 结果对象

```text

success：请求是否成功完成当前动作。
request_id、request_type、side：回指请求身份。
error / error_code：稳定失败原因；成功时为空。
error_key：battle.error.{error_code} 本地化 key；成功时为空。
events：本请求产生的 BattleEvent 深副本。
state_changes：phase_before、phase_after、messages_added 等结果摘要。
```

失败必须返回 error_code。UI 根据 error_code 显示本地化文本。

### 21.4 CardRef 生命周期

```text
card_ref：战斗内卡牌实例引用。
card_id：卡牌数据库 id。

owner_side：原拥有者阵营。
controller_side：当前控制者阵营。

```

规则：


### 21.5 UnitRef 生命周期



### 21.6 ZoneRef 生命周期

```text

```

规则：


### 21.7 EventRef / ChainRef / LinkRef 生命周期

```text

LinkRef：本场响应链链节引用。
```

规则：

```text

战斗结束后全部失效。
战斗记录可以保存事件摘要，不保存可继续操作的 EventRef。
测试可使用事件摘要断言，不直接持有 UI 节点。
```

### 21.8 引用失效规则

```text

链节结算完成：不能再被反制。
```

规则层必须在使用引用前校验引用状态。失效引用返回 error.ref.invalid 或更具体错误码。

## 24. 表现层、资源管线和反馈系统

### 24.1 表现层边界

```text

表现层负责动画、VFX、音频、浮字、屏幕反馈、UI 提示和状态展示。

```

### 24.2 表现路由模块

```text
BattleAnimationRouter.gd：战斗事件到动画 cue。
BattleVFXRouter.gd：战斗事件到 VFX 事件。
BattleAudioRouter.gd：战斗事件到音频事件。

VisualPlaybackQueue.gd：表现播放队列、优先级、合并和节流。
```

Router 只做事件到表现指令的映射，不写规则判定，不直接读取隐藏信息，不私自生成战斗结果。

### 24.3 视觉 profile

```text
CardVisualProfile：卡图、卡框、卡背、类型图标、稀有表现、施法 VFX、命中 VFX、悬停表现。
UnitVisualProfile：立绘、战斗头像、攻击动画、防御动画、受击动画、死亡动画、召唤动画。

```

视觉 profile 只保存资源引用和表现配置。规则层不硬写贴图、动画、粒子、音效或 UI 样式路径。

### 24.4 动画、VFX 和音频定义

```text
AnimationCueDefinition：动画 id、目标类型、播放层级、播放时长、是否阻塞后续表现。
VFXEventDefinition：VFX id、挂点、跟随对象、持续时间、销毁规则、叠加规则。
AudioEventDefinition：音频 id、音量组、优先级、随机变体、冷却、是否允许重叠。
FeedbackEventDefinition：浮字、屏幕震动、闪光、按钮反馈、错误提示等表现定义。
```

动画、VFX、音频和浮字通过事件映射触发。卡牌数据可以引用表现 id，但不能引用场景节点路径或脚本函数。

### 24.5 战斗表现生命周期

```text
一次性效果表现：随对应 BattleEvent 播放，播放完成后销毁。
持续效果表现：绑定永续卡、装备、附着物、状态或单位来源。来源失效后表现停止。
盖伏表现：己方显示可查看信息；敌方只显示隐藏占位。
响应链表现：链节形成、反制、结算、跳过和锁定通过统一反馈映射。
死亡和离场表现：按事件顺序播放，不提前修改规则状态。
```

持续表现不得自行延长规则效果。规则来源失效时，表现必须停止或切换为离场表现。

### 24.6 占位资源和正式资源替换

```text
占位资源放入 res://assets/placeholders/。
正式美术放入 res://assets/art/ 对应分类。
正式音频放入 res://assets/audio/ 对应分类。
正式 VFX 资源放入 res://assets/art/effects/ 或 shader / material 对应目录。
资源替换只更新视觉 / 音频 / 反馈 profile，不改战斗规则。
授权信息写入 `assets/licenses/`，资源数据库只保存 canonical id、路径和 fallback。
```

占位资源必须可被正式资源替换。长期资源路径由数据库和 profile 管理，不写入核心规则脚本。

新玩法若影响整轮探索，进入 RunModifier 或 GameMode 层。新玩法若影响单场战斗，进入对应 Battle Rules。新玩法若只影响展示，进入 UI / Visual / Audio / Feedback 层。

### 25.3 扩展接入边界

```text
不得为新玩法直接改写 BattleManager 主流程。
不得让新玩法直接修改 BattleContext 内部状态。
不得把跨战斗效果塞进单场 BattleContext。
不得把永久成长塞进 RunState。
不得让表现资源承担规则条件。
不得通过 UI 面板私自启用玩法效果。
```

扩展能力必须有明确承载层、数据字段、测试入口和文档归属。

### 25.4 复杂效果施工路径

```text
新增复制 / 改写 / 替代 / 免疫 / 控制权类效果：
1. 更新 游戏规则总纲.md 的对应规则。
2. 在本架构文档确认承载 Rules 模块。
3. 更新 effect_type / flags / filters 枚举。
4. 更新 EffectStep 字段和数据校验。
5. 在 EffectResolver 调用对应 Rules，不写单卡分支。
6. 补充规则测试、响应链测试和区域移动测试。
7. 若需要表现，补充 visual / audio / feedback profile。
```

### 25.5 新玩法施工路径

```text
新增整轮玩法：GameModeRules / RunModifierRules / RunState / SaveData / 数据表 / UI 入口。
新增战斗玩法：Battle Rules / BattleContext / EffectStep / 事件 / 测试。
新增奖励玩法：RewardService / CardPoolRules / CardAcquisitionRules / 数据表。
新增局外玩法：MetaProgression / SaveData / ProgressionDatabase / CharacterPrep UI。
新增表现玩法：VisualProfile / VFXEvent / AudioEvent / FeedbackRouter。
```

新玩法不得先在场景脚本或 UI 里临时实现，再反向补规则。

## 27. 测试和验证


### 27.2 必测规则样例

事件 / 引用：

```text
战斗事件字段完整。
隐藏事件不向 UI 暴露详情。
战斗结束后运行引用失效。
失效 CardRef 不能继续发动。
离场 UnitRef 不能作为普通目标。
响应链关闭后不能追加链节。
已结算链节不能再反制。
```

响应链：

```text
无候选不弹窗。
有候选弹窗。
连续响应形成链节。
后发先至结算。
结算中不插入新链。
被反制链节不结算。
```

区域移动：

```text
发动后默认去原拥有者墓地。
除外区不回牌库。
装备破坏回原拥有者墓地。
战斗结束不污染探索层当前卡组。
```

状态：

```text
同名状态多实例。
计数器衰减。
状态标签驱散。
状态触发事件。
战斗结束清除。
```

永续 / 装备：

```text
发动时一次性效果结算。
留场持续效果生效。
来源离场后持续效果停止。
既成一次性结果不回滚。
```

探索回流：

```text
玩家生命跨战斗继承。
战斗手牌不继承。
奖励入当前卡组或备牌区。
灵石在本轮探索内保存。
修为点结算进存档。
```

## 35. 三文档字段闭合要求

《实现架构总纲》中的模块、字段和扩展口必须在《数据与内容总表》中存在承载位置。

必须闭合的字段组：

```text
CardDefinition / EffectStep。
StatusDefinition / EquipmentDefinition / AttachmentDefinition。
EnemyDeckTemplate / EncounterDefinition / DifficultyCurve。
ProgressionDefinition。
CardVisualProfile / UnitVisualProfile / StatusVisualProfile。
EffectVisualProfile / UIVisualProfile。
AnimationCueDefinition / VFXEventDefinition / AudioEventDefinition / FeedbackEventDefinition。
GameModeDefinition / RunModifierDefinition / RelicDefinition。
QuestDefinition / AchievementDefinition / ChallengeDefinition。
ComplexEffectDefinition：复制、改写、替代、免疫、目标重写、控制权变化、归属处理。
```

数据表出现的新字段，必须能归入 Database、Rules、Service、Resolver、Router、Snapshot / ViewModel、Store 或 Validation 之一。

架构总纲出现的新模块，必须能在工程目录中找到归属目录。

规则总纲出现的新玩法规则，必须能在架构总纲中找到承载模块，并能在数据总表中找到内容字段。

禁止出现：

```text
规则有定义但架构无承载模块。
架构有字段但数据表无承载位置。
数据表有内容但规则总纲无规则口径。
数据表有字段但没有校验规则。
表现资源有引用但没有资源 profile。
```
