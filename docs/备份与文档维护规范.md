# 备份与文档维护规范

## 当前结论

GitHub 仓库是当前项目的主备份和版本记录方式。日常开发里，“保存稳定版本”默认表示整理当前改动、提交到本地仓库，并推送到 GitHub。

本地压缩包不再作为日常备份方式。只有在准备做高风险操作前，才额外生成本地 `.zip` 备份。

## 常规仓库备份流程

当用户要求“备份当前版本”“保存稳定版本”或“上传到仓库”时，默认执行以下流程：

1. 检查当前改动范围，区分应保存的项目内容和临时文件。
2. 必要时先运行对应的 Godot 无头检查或定向验证。
3. 同步更新受影响的文档，尤其是 `修改记录.md` 和 `当前状态与交接说明`。
4. 只提交应进入项目历史的文件。
5. 推送到 GitHub 的 `origin/main`。
6. 回报提交编号、推送结果，以及仍未提交的本地文件。

提交内容应聚焦一次明确变化，不把测试日志、缓存、快捷方式、临时压缩包混入仓库。

## GitHub 仓库的作用

- 保存多个历史版本，后续可以回看某个阶段做了什么。
- 对比两个版本之间的差异，定位某次改动引入的问题。
- 在改坏后恢复单个文件、某一批改动，或在确认后回到旧版本。
- 在大改前建立清晰存档点，降低重构和删改风险。
- 后续可以使用分支做高风险实验，稳定后再合并回主线。
- 未来如果需要，也可以用 issue、标签、release 管理任务和阶段版本。

## 本地压缩包备份

只有以下情况才考虑额外生成本地压缩包：

- 大范围代码重排。
- 批量迁移数据格式。
- 删除大量可运行内容或资源。
- 批量移动美术、音频、导出配置等资源。
- 尝试不熟悉工具或自动化操作，且可能影响大量文件。

本地备份规则：

- 备份放在 `backups/`。
- 使用 `.zip`。
- 文件名包含日期和主题，例如 `太玄宗-备份-20260707-战斗清理.zip`。
- 最多保留最近 3 个压缩包。

备份应包含：

- `docs/`
- `scenes/`
- `scripts/`
- `project.godot`
- 基础配置文件和图标。

备份不包含：

- `.git/`
- `.godot/`
- `.godot_user/`
- `.agents/`
- `.codex/`
- `.godot_test_logs/`
- `backups/`
- 日志文件。
- 快捷方式文件。
- 未来大型导出产物或缓存。

## 文档维护

- 主文档只保留当前阶段有效信息。
- 不再把旧方案移入主文档或堆成历史段落。
- 阶段性变化写入 `修改记录.md`。
- 影响新对话接手的信息同步到 `当前状态与交接说明`。
- 改系统边界、依赖方向、模块职责或长期重构路线同步到 `架构拆分与商业化迭代约束`。
- 改规则同步到 `游戏设计总览`。
- 改交互同步到 `UI与交互规范`。
- 改数据结构同步到 `数据表与内容配置规划`。
- 改备份、提交或恢复规则同步到本文档。

## 验证方式

Git 用于判断“哪些文件要进入版本记录”和“本地是否已经推送到 GitHub”；不直接证明游戏功能正确。

实际功能改动后优先使用：

- 定向文本搜索。
- Godot 无头检查。
- 必要时手动打开 Demo 体验。
