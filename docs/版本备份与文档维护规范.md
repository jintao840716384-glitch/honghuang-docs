# 版本备份与文档维护规范

## 当前结论

当前阶段先以本地压缩备份为主。项目还没有正式美术、音乐和大型外部素材，体积主要来自脚本、场景和文档，因此没有必要做多个完整展开目录。

本地备份规则：

- 只保留最近 3 个压缩包。
- 备份文件放在 `backups/`。
- 备份格式使用 `.zip`。
- 文件名包含日期和阶段说明。
- 不保留多个展开版工程目录。
- 高风险大改前可以手动多做一个临时压缩包，但确认稳定后要清理旧包。

当前备份应包含：

- `docs/`
- `scenes/`
- `scripts/`
- `project.godot`
- `.editorconfig`
- `.gitattributes`
- `.gitignore`
- `icon.svg`
- `icon.svg.import`

当前备份不包含：

- `.godot/`
- `.godot_user/`
- `.agents/`
- `.backup_git/`
- `backups/` 内部的其他备份或临时上传目录
- `.godot_test*.log`
- 未来的大型导出产物、缓存和临时文件

等正式美术、音乐、视频等素材进入项目后，再单独评估素材备份策略。届时可能需要 Git LFS、网盘素材库，或代码仓库与素材仓库分离。

## 备份策略

推荐使用 GitHub 作为主备份，不建议长期在项目目录内复制多个完整备份文件夹。

原因：

- GitHub 能记录每次改动。
- 可以回退到任意提交。
- 不会混淆当前版本和备份版本。
- 适合 Demo 阶段频繁试错。

## 本地备份

本地轮转备份可以作为临时手段，但只建议在以下情况使用：

- 准备做高风险大改前。
- 网络不可用，暂时无法提交远程。
- 需要保存一个可直接复制运行的压缩快照。

如果做本地备份，建议最多保留 3 个压缩包，不建议保留多个展开目录。

## Git 提交建议

Demo 阶段建议按阶段提交：

- 战斗规则可跑通。
- UI 交互完成一轮。
- 视觉反馈完成一轮。
- 音效占位完成一轮。
- 探险地图外壳完成一轮。
- 文档整理完成一轮。

提交信息建议简短明确，例如：

- `docs: organize prototype documentation`
- `feat: add exploration map shell`
- `fix: stabilize card tooltip first render`

## 文档维护频率

- `修改记录.md`：每次阶段性更新后补一句或几句。
- `当前状态与交接说明`：每次会影响新对话接手的信息都更新。
- 设计文档：当规则、交互或素材方向确定后再更新。
- 数据库文档：内容数量开始变多时再细化。
