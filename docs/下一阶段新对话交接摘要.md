# 下一阶段新对话交接摘要

## 使用场景

本文件用于结束本次架构优化对话后，开启下一轮玩法、内容或数值设计对话。它不是新的设定文档，也不替代 `当前状态与交接说明` 和 `架构拆分与商业化迭代约束`，只负责告诉下一轮接手者：当前底座已经拆到什么程度，后续默认应该怎样继续。

## 当前阶段结论

- 第一轮框架级拆分已经完成，可以先停止“为了拆而拆”。
- 当前更适合进入真实内容迭代：新卡牌、新敌人、新敌方卡组、新事件、新职业差异和数值验证。
- 后续新增功能时，默认先对照 `架构拆分与商业化迭代约束.md` 判断归属；用户不需要每次额外提醒“注意架构”。
- 小需求也不能绕过已有模块。能用数据字段、通用规则步骤、规则服务、展示工厂、素材数据库或本地化文本解决的，不要写单独长期逻辑。
- 若必须做临时特例，必须在回复和文档中说明它是临时特例，并记录最终应该归属的模块。

## 下一轮不要重复引入

- 不要重新引入同名卡数量限制、稀有度式禁限、强制删牌式肉鸽逻辑。
- 不要恢复局内 Boss 后境界突破流程；当前成长方向是局外修为点和职业成长。
- 不要把玩家职业当成特殊玩家对象；职业是初始牌组、职业卡池、局外成长和主单位引用的包装。
- 不要做传统可见手动存档槽；当前方向是单用户自动保存设置和局外成长。
- 不要为了新界面、新卡、新敌人或新事件绕过现有数据层、规则层、UI 展示层和表现层。

## 下一轮适合开始的任务

优先从真实内容开始，而不是继续扩大底层拆分：

1. 设计并落地第一批更完整的剑修、符修低分卡和职业核心牌。
2. 设计低层普通敌人、精英敌人和 Boss 牌包，用现有敌方卡组模板体系验证敌方牌手框架。
3. 扩展事件、宝箱、坊市和休息节点内容，检验奖励、商店、事件和入卡去向服务是否足够通用。
4. 通过固定种子无头探针看趋势，再决定是否调成长价格、卡组总分、敌方血攻和奖励池。

## 验证要求

下一轮每次改动后，不要只看 `git diff` 或 `git status`。至少按改动范围执行：

- 小内容改动：定向文件检查，加 `PrototypeSmokeTest.gd`。
- 探索 / 地图 / 奖励 / 商店 / 事件改动：加 `RunFlowSmokeTest.gd`。
- UI 布局、设置或展示改动：加 `LayoutSmokeTest.gd`。
- 数值和成长趋势改动：加 `SwordProgressionProbe.gd` 或同类固定种子探针。
